# CM-06: Semantic Vector-Based Context Management

## Category
Context Management (CM)

## Description
Semantic Vector-Based Context Management uses vector embeddings and similarity search for intelligent context storage and retrieval instead of traditional key-value or chronological approaches. By encoding context segments as semantic vectors, this technique enables relevance-based retrieval where the AI system automatically loads the most contextually relevant information based on the current task, rather than relying on recency or keyword matching.

## When to Use

Use Semantic Vector-Based Context Management when:

1. **Massive Context Repositories**: Projects with years of development history, extensive documentation, or large codebases
2. **Cross-Project Knowledge Transfer**: Need to find relevant patterns from past projects applicable to current work
3. **Intelligent Context Recommendations**: Want AI to suggest relevant context based on semantic similarity, not just keywords
4. **Long-Running AI Workflows**: Persistent agents working across multiple sessions with selective context loading
5. **RAG (Retrieval-Augmented Generation) Systems**: Building production AI systems that augment prompts with relevant context
6. **Context Search at Scale**: Traditional keyword search is inadequate for finding semantically similar content

## Pattern

### Structural Template

```markdown
## Context Management Strategy

### 1. Context Encoding
For each context segment:
- **Segment Identification:** {SEGMENT_TYPE} (code module, architectural decision, bug fix, feature)
- **Generate Embedding:** Use embedding model (e.g., text-embedding-3-small) to create vector representation
- **Store in Vector Database:** Pinecone / Weaviate / Qdrant / Chroma with metadata

### 2. Metadata Schema
```json
{
  "id": "unique_segment_id",
  "content": "The actual context content",
  "embedding": [0.123, -0.456, ...], // 1536-dimensional vector
  "metadata": {
    "type": "architectural_decision | code_change | bug_fix | feature",
    "timestamp": "2024-01-15T10:30:00Z",
    "project": "project_name",
    "author": "developer_name",
    "tags": ["authentication", "security", "oauth"],
    "file_path": "src/auth/oauth.py"
  }
}
```

### 3. Semantic Retrieval
When resuming work or starting new task:
- **Query:** Current task description or question
- **Generate Query Embedding:** Encode query as vector
- **Similarity Search:** Query vector database (cosine similarity)
- **Rank Results:** Top-K most semantically similar context segments
- **Load Context:** Include top results within token budget

### 4. Hybrid Search (Optional)
Combine semantic + keyword + metadata filters:
- **Semantic:** Vector similarity (primary ranking)
- **Keyword:** BM25 full-text search (recall boost)
- **Filters:** Metadata constraints (project, date range, author)
```

# Context Management System for Development Team

## Phase 1: Context Segmentation and Encoding

### Context Segments to Encode

**Type 1: Architectural Decisions**
```markdown
# Example Architectural Decision Record

**Decision:** Use event-driven architecture for order processing
**Context:** E-commerce system processes 10K orders/day with complex workflows
**Options Considered:**
1. Synchronous REST calls (rejected - tight coupling)
2. Message queue (selected - loose coupling, retry logic)
3. Database polling (rejected - inefficient)

**Consequences:**
- Pro: Services can fail independently without blocking orders
- Pro: Easy to add new order processing steps
- Con: Eventually consistent (order status may lag)

**Implementation:** RabbitMQ with dead-letter queues
**Date:** 2023-05-15
**Project:** E-commerce
```

**Encoding Process:**
```python
import openai
from pinecone import Pinecone

# Initialize
client = openai.OpenAI(api_key="...")
pc = Pinecone(api_key="...")
index = pc.Index("development-context")

# Generate embedding
content = """
Decision: Use event-driven architecture for order processing.
Context: E-commerce system processing 10K orders/day with complex workflows.
Selected message queue over synchronous REST for loose coupling and retry logic.
Implemented with RabbitMQ and dead-letter queues.
Tradeoff: Eventually consistent order status.
"""

embedding_response = client.embeddings.create(
    model="text-embedding-3-small",
    input=content
)
embedding = embedding_response.data[0].embedding  # 1536-dimensional vector

# Store in vector database
index.upsert([(
    "adr-001-event-driven-orders",  # Unique ID
    embedding,  # Vector
    {  # Metadata
        "type": "architectural_decision",
        "project": "ecommerce",
        "timestamp": "2023-05-15T00:00:00Z",
        "tags": ["event-driven", "rabbitmq", "order-processing"],
        "title": "Event-driven architecture for order processing",
        "content": content
    }
)])

print("✅ Stored architectural decision with semantic embedding")
```

**Type 2: Bug Fixes**
```markdown
# Bug Fix: Memory Leak in Image Upload

**Issue:** Server memory grows indefinitely when processing images
**Root Cause:** Uploaded images stored in memory, never released
**Solution:** Stream images directly to S3, don't buffer in memory
**Code Changes:**
- Before: `image_data = request.files['image'].read()` (loads entire file)
- After: `s3.upload_fileobj(request.files['image'], bucket, key)` (streams)

        "type": "bug_fix",

## Phase 2: Semantic Retrieval in Action

### Scenario: Developer Starts New Task

**New Task:** "Implement video upload feature for mobile app"

**Developer Question:** "What relevant patterns exist for handling large file uploads?"

### Retrieval Process

```python
# Step 1: Encode the query
query = "How to handle large file uploads efficiently without using too much memory"

query_embedding = client.embeddings.create(
    model="text-embedding-3-small",
    input=query
).data[0].embedding

# Step 2: Semantic search in vector database
results = index.query(
    vector=query_embedding,
    top_k=10,
    include_metadata=True,
    filter={
        "project": {"$in": ["mobile-app-backend", "ecommerce", "api-gateway"]},
        # Filter to relevant projects
    }
)

# Step 3: Results ranked by semantic similarity
for match in results['matches']:
    print(f"Similarity: {match['score']:.3f}")
    print(f"Type: {match['metadata']['type']}")
    print(f"Title: {match['metadata']['title']}")
    print(f"Project: {match['metadata']['project']}")
    print(f"Date: {match['metadata']['timestamp']}")
    print("---")
```

## Phase 3: Context Loading with Token Budget

### Scenario: Resume Work on Analytics Dashboard

**Current Task:** "Add real-time user activity dashboard"

**Available Token Budget:** 8,192 tokens (Claude context window reserved for this)

### Smart Context Loading

```python
# Step 1: Semantic search for relevant context
query = "Building real-time dashboards with live updates from multiple data sources"
query_embedding = client.embeddings.create(
    model="text-embedding-3-small",
    input=query
).data[0].embedding

results = index.query(
    vector=query_embedding,
    top_k=50,  # Get more than we need
    include_metadata=True
)

# Step 2: Prioritize and load within token budget
def estimate_tokens(text):
    return len(text.split()) * 1.3  # Rough approximation

selected_contexts = []
total_tokens = 0
token_budget = 8192

for match in results['matches']:
    context_content = match['metadata']['content']
    context_tokens = estimate_tokens(context_content)

    if total_tokens + context_tokens <= token_budget:
        selected_contexts.append({
            'content': context_content,
            'similarity': match['score'],
            'type': match['metadata']['type'],
            'project': match['metadata']['project']
        })
        total_tokens += context_tokens
    else:
        break  # Budget exhausted

print(f"Loaded {len(selected_contexts)} context segments")
print(f"Token usage: {total_tokens}/{token_budget} ({total_tokens/token_budget*100:.1f}%)")

# Step 3: Construct prompt with semantically relevant context
prompt = f"""
You are helping build a real-time user activity dashboard.

## Relevant Context from Past Work

{chr(10).join([
    f"### {ctx['type'].replace('_', ' ').title()} (Similarity: {ctx['similarity']:.2f})\\n{ctx['content']}"
    for ctx in selected_contexts
])}

## Current Task

Add real-time user activity dashboard showing:
- Active users (last 5 minutes)
- Current sessions by page
- Live event stream

Based on the relevant patterns above, recommend an approach.
"""
```

**Result:**
```
Loaded 12 context segments
Token usage: 7,850/8,192 (95.8%)

Context loaded:
1. WebSocket architecture for real-time updates (similarity: 0.91)
2. Redis pub/sub for event distribution (similarity: 0.89)
3. Server-Sent Events vs WebSocket tradeoffs (similarity: 0.87)
4. Dashboard state management patterns (similarity: 0.85)
5. Time-series data aggregation (similarity: 0.83)
... (7 more relevant patterns)
```

### Variation 3: Temporal Decay with Semantic Relevance

Combine semantic similarity with recency weighting:

```python
def calculate_score(semantic_score, timestamp):
    age_days = (datetime.now() - timestamp).days
    recency_score = math.exp(-age_days / 180)  # Decay over 6 months

    # Weighted combination
    final_score = 0.7 * semantic_score + 0.3 * recency_score
    return final_score
```

## Pitfalls

### Pitfall 1: Poor Chunking Strategy
**Problem:** Encoding entire documents or too-small fragments

**Example (BAD):**
```python
# Entire 10,000-word design document as single embedding
content = entire_design_doc  # Loses semantic granularity
embedding = create_embedding(content)
```

**Solution:** Chunk at semantic boundaries (decisions, modules, functions)

**Example (GOOD):**
```python
# Chunk by architectural decision
for decision in architectural_decisions:
    embedding = create_embedding(decision.content)  # Each decision separate
```

### Pitfall 2: Metadata Poverty
**Problem:** Storing vectors without rich metadata for filtering

**Example (BAD):**
```python
index.upsert([(id, embedding, {"content": text})])  # Only content, no metadata
```

**Solution:** Store comprehensive metadata

**Example (GOOD):**
```python
index.upsert([(id, embedding, {
    "content": text,
    "type": "bug_fix",
    "project": "ecommerce",
    "author": "alice",
    "timestamp": "2024-01-15",
    "tags": ["performance", "database"],
    "severity": "high",
    "file_path": "src/db/queries.py"
})])
```

### Pitfall 3: Using Wrong Embedding Model
**Problem:** Using generic embeddings for code or domain-specific content

**Example (BAD):**
```python
# Using general-purpose embedding for code
code_embedding = create_embedding(code_snippet, model="text-embedding-3-small")
# May not capture code semantics well
```

**Solution:** Use specialized embeddings for different content types

**Example (GOOD):**
```python
# Use code-specific embeddings
code_embedding = create_embedding(code_snippet, model="code-embedding-ada-002")

# Use general embeddings for documentation
doc_embedding = create_embedding(documentation, model="text-embedding-3-small")
```

### Pitfall 4: Not Updating/Expiring Context
**Problem:** Outdated context pollutes search results

**Example (BAD):**
```python
# Decision from 2020 about using Python 2.7
# Still returned as relevant in 2024 (Python 2.7 is dead!)
```

**Solution:** Add expiration or version metadata

**Example (GOOD):**
```python
metadata = {
    "content": "Use Python 2.7 for compatibility",
    "deprecated": True,
    "deprecated_date": "2020-01-01",
    "superseded_by": "decision-456-python-3"
}

# Query filter
filter={"deprecated": {"$ne": True}}
```

### Pitfall 5: Ignoring Semantic Similarity Thresholds
**Problem:** Including low-relevance results that confuse the AI

**Example (BAD):**
```python
results = index.query(vector=query_embedding, top_k=100)
# Includes results with similarity 0.3 (barely relevant)
```

**Solution:** Filter by minimum similarity threshold

**Example (GOOD):**
```python
results = index.query(vector=query_embedding, top_k=100)
filtered_results = [r for r in results['matches'] if r['score'] >= 0.75]
# Only include reasonably similar results
```

## Summary

Semantic Vector-Based Context Management (CM-06) transforms context retrieval from simple keyword matching or chronological ordering to intelligent, relevance-based discovery. By encoding context as semantic vectors, AI systems can find genuinely relevant information even when exact keywords don't match, enabling cross-project knowledge transfer and intelligent context recommendations.

**Key Takeaway:** If your AI system manages large amounts of context and needs to find relevant information intelligently (not just recent or keyword-matched), implement semantic vector-based context management with a vector database.
