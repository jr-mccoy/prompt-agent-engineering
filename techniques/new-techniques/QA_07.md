# QA-07: Statistical A/B Testing for Prompts

## Category
Quality Assurance (QA)

## Description
Statistical A/B Testing for Prompts applies rigorous experimental methods to systematically compare prompt variations and measure improvement objectively. Instead of subjectively judging whether a new prompt is better, this technique splits traffic between variants, collects performance data, applies statistical tests to determine significance, and makes data-driven deployment decisions based on quantitative evidence rather than intuition.

## When to Use

Use Statistical A/B Testing for Prompts when:

1. **Validating Improvements**: Need objective evidence that new prompt performs better than current version
2. **Production AI Systems**: Deploying prompts to live users where data-driven decisions are critical
3. **Continuous Improvement**: Regularly testing variations to optimize prompt performance
4. **Comparing Multiple Approaches**: Need to choose between 2+ prompt strategies objectively
5. **Preventing Subjective Bias**: Team disagrees on which prompt is better (let data decide)
6. **Demonstrating ROI**: Need quantitative proof of improvement for stakeholders

4. Calculate p-value
5. Compute confidence intervals
6. Calculate effect size (Cohen's h or Cohen's d)

### Complete Working Example: Customer Support Prompt A/B Test

```markdown
# A/B Test: Improved Customer Support Prompt

## Test Overview

**Objective:** Validate that new empathy-focused prompt improves customer satisfaction

**Hypothesis:**
- H₀ (Null): New prompt success rate = Current prompt success rate (87%)
- H₁ (Alternative): New prompt success rate > Current prompt success rate

**Primary Metric:** Issue Resolution Rate
- Definition: % of customer issues resolved without human escalation
- Current Baseline: 87%
- Target Improvement: ≥ 5 percentage points (absolute) → 92%

**Business Context:**
- 10,000 customer interactions/day
- Human escalation costs $15/ticket
- 1% improvement in resolution = $15,000/year savings

---

## Variant Definitions

### Variant A (Control): Current Production Prompt

```markdown
You are a customer support agent. Resolve customer issues following company policies.

When customer contacts you:
1. Identify issue type
2. Apply relevant policy (refunds, returns, shipping)
3. Provide solution
```

**Known Performance (Last 30 Days):**
- Resolution Rate: 87%
- Customer Satisfaction: 4.2/5.0
- Average Response Time: 2.1 seconds

---

### Variant B (Treatment): Empathy-Focused Prompt

```markdown
You are a customer support agent. Resolve customer issues following company policies
while showing empathy and understanding.

When customer contacts you:
1. **Acknowledge their concern:** "I understand how frustrating that must be..."
2. Identify issue type
3. **Show empathy again:** "I'd be upset too if that happened to me..."
4. Apply relevant policy (refunds, returns, shipping)
5. Provide solution
6. **End with reassurance:** "I'm here to make this right for you."

**Tone Guidelines:**
- Use empathetic language ("I understand," "I appreciate your patience")
- Acknowledge frustration before offering solutions
- Personalize responses (use customer name)
```

**Hypothesis:** Adding empathy will:
- Increase resolution rate (customers more patient with policy-compliant solutions)
- Increase customer satisfaction
- Potentially increase response time (longer, more personalized responses)

---

## Sample Size Calculation

### Statistical Parameters

- **Baseline Success Rate (p₁):** 0.87 (87%)
- **Target Success Rate (p₂):** 0.92 (92%)
- **Minimum Detectable Effect:** 0.05 (5 percentage points)
- **Significance Level (α):** 0.05
- **Statistical Power (1-β):** 0.80

### Calculation

```python
from statsmodels.stats.proportion import proportion_effectsize, samplesize_proportions_2indep_onetail

# Effect size (Cohen's h)
baseline = 0.87
target = 0.92
effect_size = proportion_effectsize(baseline, target)
# Result: effect_size = 0.151 (small-to-medium effect)

# Sample size per group
n_per_group = samplesize_proportions_2indep_onetail(
    effect_size=0.151,
    alpha=0.05,
    power=0.80,
    ratio=1.0  # Equal allocation
)
# Result: n_per_group = 691

# Total sample size
total_n = n_per_group * 2
# Result: total_n = 1,382 interactions needed
```

**Required Samples:**
- Variant A: 691 interactions
- Variant B: 691 interactions
- **Total: 1,382 interactions**

### Test Duration

**Daily Traffic:** 10,000 interactions/day
**Allocation:** 50% A, 50% B (5,000 each/day)
**Duration:** 1,382 / 10,000 = **0.14 days ≈ 4 hours**

**Decision:** Run for 24 hours to account for time-of-day variations
**Total Sample (24 hours):** 10,000 interactions (5,000 per variant)

## Traffic Allocation

### Randomization Strategy

**Method:** Deterministic hash-based (same customer always gets same variant)

**Implementation:**
```python
import hashlib

def assign_variant(customer_id):
    """Assign customer to variant deterministically"""
    # Hash customer ID
    hash_value = int(hashlib.md5(customer_id.encode()).hexdigest(), 16)

    # 50/50 split
    if hash_value % 2 == 0:
        return "variant_a"  # Control
    else:
        return "variant_b"  # Treatment

# Usage
variant = assign_variant("customer-12345")
if variant == "variant_a":
    response = support_agent_v1(customer_message)  # Control
else:
    response = support_agent_v2(customer_message)  # Treatment

# Log for analysis
log_interaction(customer_id, variant, resolved, satisfaction, response_time)
```

**Why Deterministic?**
- Same customer gets consistent experience (no variant switching mid-conversation)
- Prevents "bucket contamination" (learning from different prompts)

nobs = [5000, 5000]     # Total observations

print(f"Z-statistic: {z_stat:.3f}")
print(f"P-value: {p_value:.4f}")

# Results:
# Z-statistic: 4.831
# P-value: 0.0000007 (very strong significance)
```

### Confidence Interval

```python
from statsmodels.stats.proportion import proportion_confint

# 95% Confidence interval for difference
diff = 0.905 - 0.872
se_diff = ((0.872 * (1-0.872) / 5000) + (0.905 * (1-0.905) / 5000)) ** 0.5
ci_lower = diff - 1.96 * se_diff
ci_upper = diff + 1.96 * se_diff

print(f"Improvement: {diff*100:.1f}%")
print(f"95% CI: [{ci_lower*100:.1f}%, {ci_upper*100:.1f}%]")

# Results:
# Improvement: 3.3%
# 95% CI: [2.2%, 4.4%]
```

## Pitfalls

### Pitfall 1: Insufficient Sample Size

**Problem:** Calling test too early, false significance

**Example (BAD):**
```markdown
After 100 samples per variant:
- A: 85% (85/100)
- B: 95% (95/100)
- p = 0.03

**Decision:** "B is better! Deploy!"

**Truth:** With only 100 samples, high chance of false positive (power too low)
```

**Solution:** Calculate required sample size first

### Pitfall 2: Peeking at Results

**Problem:** Checking p-values repeatedly, stopping when p < 0.05

**Example (BAD):**
```markdown
Check 1 (n=100): p = 0.12 (continue)
Check 2 (n=300): p = 0.08 (continue)
Check 3 (n=500): p = 0.04 (STOP! p < 0.05!)

**Problem:** Inflated false positive rate (should be 5%, actually ~25%)
```

**Solution:** Pre-specify sample size, analyze only once OR use sequential testing methods

### Pitfall 3: Ignoring Practical Significance

**Problem:** Deploying statistically significant but practically useless improvements

**Example (BAD):**
```markdown
**Result:** 87.0% → 87.1% (+0.1%, p < 0.01)

**Decision:** "Statistically significant, deploy!"

**Reality:** 0.1% improvement has zero business impact
```

**Solution:** Require minimum practical effect size (e.g., ≥2%)

### Pitfall 4: Not Accounting for Variance Across Time

**Problem:** Testing only during one time period

**Example (BAD):**
```markdown
Test Duration: Monday 9am-5pm
Result: B significantly better

**Deployment:** B to all traffic
**Production (Tuesday):** B performs worse (evening traffic differs)
```

**Solution:** Test across full cycle (24 hours, full week, etc.)

### Pitfall 5: Data Quality Issues

**Problem:** Contaminated or biased data

**Example (BAD):**
```markdown
Test setup:
- Variant A: Deployed to mobile app only
- Variant B: Deployed to web app only

**Result:** B better (95% vs. 85%)

**Problem:** Not testing prompts, testing web vs. mobile!
```

**Solution:** Proper randomization, check for Simpson's Paradox

## Summary

Statistical A/B Testing for Prompts (QA-07) provides objective, data-driven validation of prompt improvements through rigorous experimental methods. By splitting traffic between variants, collecting sufficient samples for statistical power, applying appropriate statistical tests, and making decisions based on quantitative evidence, this technique prevents deploying regressions and ensures prompt changes genuinely improve performance.

**Key Takeaway:** Never deploy prompt improvements based on subjective judgment alone. Use statistical A/B testing with proper sample sizes, significance testing, and practical significance thresholds to validate improvements objectively before full rollout.
