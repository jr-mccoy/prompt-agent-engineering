# AG-15: Staged Rollout with Automatic Rollback

## Category
Agentic (AG)

## Description
Staged Rollout with Automatic Rollback progressively deploys improved AI agents through incremental traffic stages (Alpha 5% → Beta 20% → Canary 50% → Full 100%) with automated rollback triggers for production safety. Instead of deploying changes directly to 100% of users, this technique mitigates risk by exposing new agent versions to progressively larger user populations while continuously monitoring success metrics and automatically reverting to the previous version if quality degrades beyond acceptable thresholds.

## When to Use

Use Staged Rollout with Automatic Rollback when:

1. **Production AI Agents**: Deploying improved prompts, models, or agent logic to live traffic
2. **High-Stakes Applications**: Systems where failures impact revenue, safety, or compliance (healthcare, finance, legal)
3. **Continuous Improvement**: Regularly updating AI systems based on performance data
4. **Risk Mitigation**: Need to prevent catastrophic failures from reaching all users
5. **Deployment Confidence**: Want data-driven validation before full rollout
6. **Rollback Capability Required**: Must be able to quickly revert bad deployments

## Rollback Procedures

### Automatic Rollback
Triggered automatically when metrics breach thresholds

**Rollback Actions:**
1. Immediately shift 100% traffic to stable version (v1.2.0)
2. Alert on-call team
3. Generate rollback report with triggering metrics
4. Preserve new version deployment for investigation

### Manual Rollback
Triggered by on-call engineer or stakeholder

**Trigger Command:**
```bash
./rollback.sh --version v1.2.0 --reason "manual-trigger"
```

## Rollback Decision Matrix

| Metric | Threshold | Action | Urgency |
|--------|-----------|--------|---------|
| Success rate drop | >10% | IMMEDIATE ROLLBACK | Critical |
| Critical errors | >5% increase | IMMEDIATE ROLLBACK | Critical |
| P95 latency | >3x baseline | ROLLBACK WITHIN 1 HOUR | High |
| Cost per task | >20% increase | ROLLBACK WITHIN 4 HOURS | Medium |
| User complaints | >3x baseline | ROLLBACK WITHIN 1 HOUR | High |
| Manual trigger | Any time | ROLLBACK IMMEDIATELY | Variable |
```

- Expected Improvements:
  - Success rate: 87% → 92% (+5 percentage points)
  - Response quality: Better explanations, fewer follow-ups
  - Cost: $0.05 → $0.07 (+40% due to longer prompts, but fewer escalations)

**Risk Assessment:**
- Impact: 50,000 customer interactions/day
- Revenue risk: $500K/day if agent fails completely
- Reputation risk: High (customer-facing)
- Rollback requirement: Critical

**Decision:** Use staged rollout with automatic rollback

## Stage 1: Alpha Rollout (5% of Traffic)

**Start Date:** 2024-01-15 00:00 UTC

**Traffic Allocation:**
- v2.0 (New): 5% (2,500 interactions/day)
- v1.5 (Current): 95% (47,500 interactions/day)

**Implementation:**
```python
# Traffic routing logic
import random

def route_customer_request(customer_id, request):
    # Deterministic routing based on customer_id hash
    # (same customer always gets same version for consistency)
    traffic_assignment = hash(customer_id) % 100

    if traffic_assignment < 5:  # 5% to new version
        return support_agent_v2.handle(request)
    else:  # 95% to current version
        return support_agent_v1_5.handle(request)
```

**Success Criteria:**

| Metric | Baseline (v1.5) | Target (v2.0) | Status |
|--------|-----------------|---------------|--------|
| Success Rate | 87% | ≥ 87% | ✅ 89% (Day 1) |
| Error Rate | 2% | < 2% | ✅ 1.5% (Day 1) |
| P95 Latency | 3.2s | < 5s | ✅ 3.8s (Day 1) |
| Cost/Interaction | $0.05 | < $0.06 | ⚠️ $0.07 (Day 1) |
| Complaints | 10/day | < 15/day | ✅ 8/day (Day 1) |

**Day 1 Analysis:**

✅ **Success Rate:** 89% (vs. baseline 87%)
- Improvement: +2 percentage points
- Statistical significance: p < 0.05 (sample: 2,500 interactions)

✅ **Error Rate:** 1.5% (vs. baseline 2%)
- Reduction: -0.5 percentage points
- Fewer "I don't understand" responses

✅ **Latency:** 3.8s P95 (vs. baseline 3.2s)
- Increase: +0.6s (acceptable - due to longer reasoning)
- Still well under 5s threshold

⚠️ **Cost:** $0.07 per interaction (vs. baseline $0.05)
- Increase: +40%
- **Analysis:** Higher than expected, but success rate improvement may offset escalation costs
- **Decision:** Monitor closely; calculate ROI (fewer escalations = lower total cost)

✅ **User Complaints:** 8/day (vs. baseline 10/day)
- Reduction: -20%
- Positive signal

**Manual Review (Sample of 100 interactions):**

Reviewer examined 100 random v2.0 interactions:
- 92 resolved successfully (vs. 87 expected from v1.5)
- 5 escalated to human agent (vs. 10 expected)
- 3 unresolved (vs. 3 expected)

**Quality Assessment:**
- Response quality: Noticeably better (more detailed, empathetic)
- Edge case handling: Improved (correctly handled complex refund scenario)
- Consistency: Good (no hallucinations or policy violations)

**Stage 1 Decision: ✅ PROCEED TO STAGE 2**

Rationale: All critical metrics met or exceeded. Cost increase concerning but offset by success rate improvement and fewer escalations.

**A/B Statistical Test:**

v1_5_sample = 40000 * 2  # 80K interactions

v1_5_success_rate = 0.87
v2_0_success_rate = 0.90

# Two-proportion z-test

## Pitfalls

### Pitfall 1: No Baseline Metrics

**Problem:** Can't detect degradation without knowing current performance

**Example (BAD):**
```markdown
Stage 1: Deploy v2.0 to 5% traffic

**Question:** Is 85% success rate good or bad?
**Answer:** We don't know... we never measured v1.5

**Result:** Can't make data-driven rollout decisions
```

**Solution:** Establish baseline before rollout

**Example (GOOD):**
```markdown
Week 1: Measure v1.5 baseline
- Success rate: 87% (baseline established)
- Error rate: 2%
- Latency: 3.2s

Week 2: Deploy v2.0 to 5% traffic
- Success rate: 89% (vs. baseline 87%, +2% ✅)
- Error rate: 1.5% (vs. baseline 2%, -0.5% ✅)

**Decision:** Data-driven (v2.0 is better)
```

### Pitfall 2: Rollout Too Fast

**Problem:** Jumping stages too quickly, not enough validation time

**Example (BAD):**
```markdown
Monday 8am: Stage 1 (5%) deployed
Monday 10am: Stage 2 (20%) deployed  # Only 2 hours!
Monday 2pm: Stage 3 (50%) deployed   # Only 4 hours!
Monday 6pm: 100% deployed            # Only 10 hours!

Tuesday: Critical bug discovered affecting 100% of traffic
**Impact:** All customers affected, rushed rollback
```

**Solution:** Wait for statistical significance and sustained metrics

**Example (GOOD):**
```markdown
Day 1: Stage 1 (5%) deployed
Day 2-3: Monitor 48 hours (sufficient sample: 5K interactions)
Day 3: Stage 2 (20%) deployed (after validation)
Day 4-6: Monitor 72 hours (sample: 30K interactions)
Day 6: Stage 3 (50%) deployed
...
```

### Pitfall 3: Ignoring Rollback Triggers

**Problem:** Seeing degradation but not rolling back, hoping it improves

**Example (BAD):**
```markdown
Stage 2: 20% traffic

Hour 1: Success rate drops to 80% (baseline 87%)
**Team:** "Let's wait and see, maybe it will improve..."

Hour 2: Success rate drops to 75%
**Team:** "Still hopeful..."

Hour 6: Success rate drops to 70%
**Team:** "Finally rolling back..."

**Impact:** 6 hours of degraded service for 20% of customers = 10K affected
```

**Solution:** Automatic rollback triggers, no hesitation

**Example (GOOD):**
```markdown
Stage 2: 20% traffic

08:30: Success rate drops to 80% (baseline 87%, -7%)
08:31: Automatic rollback trigger hit (threshold: -5%)
08:32: 100% traffic back to v1.5 (stable)

**Impact:** 30 minutes of degradation for 20% of customers = 400 affected
```

### Pitfall 4: No Rollback Plan

**Problem:** Unable to rollback when needed

**Example (BAD):**
```markdown
Stage 3: 50% traffic, critical bug discovered

**Engineer:** "How do we rollback?"
**Team:** "Uh... we didn't plan for that..."
**Action:** Scramble to write rollback script
**Time to Rollback:** 4 hours (chaos)

**Impact:** 4 hours × 25,000 customers = 100K affected
```

**Solution:** Test rollback procedure before rollout

**Example (GOOD):**
```markdown
Pre-Rollout Testing:
1. Deploy v2.0 to 0% traffic (staging)
2. Test rollback: `./rollback.sh --version v1.5`
3. Validate rollback works in <1 minute
4. ✅ Rollback tested and ready

Stage 3: Critical bug discovered
**Action:** Execute tested rollback procedure
**Time to Rollback:** 1 minute

**Impact:** 1 minute × 25,000/day = 17 customers affected
```

### Pitfall 5: Forgetting About Data Consistency

**Problem:** Rollback causes data inconsistencies

**Example (BAD):**
```markdown
v2.0: Stores data in new schema
v1.5: Expects data in old schema

**Rollback:** v2.0 → v1.5
**Problem:** Data written by v2.0 unreadable by v1.5
**Impact:** Data corruption, customer data lost
```

**Solution:** Backward-compatible data changes

**Example (GOOD):**
```markdown
v2.0: Writes data in BOTH old and new schemas (dual-write)
v1.5: Reads data from old schema

**Rollback:** v2.0 → v1.5
**Result:** v1.5 can read data written by v2.0 (no corruption)

**After rollout complete:**
- Stop dual-writing
- Migrate old schema data to new schema
- Deprecate old schema
```
