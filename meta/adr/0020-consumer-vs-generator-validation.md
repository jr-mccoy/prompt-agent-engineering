# ADR-0020 — Consumer validation is not a second copy of the generator's check

## Status

Accepted. Implemented in Phase 3 as `pae validate-registry`.

## Context

`python3 scripts/generate_registry.py --check` already validates the registry,
thoroughly: it re-derives corpus membership, classifies kinds, derives UIDs
from birth paths, applies overrides, reconciles the reviewed ledgers with the
generated records, and fails if anything drifted or was hand-edited.

Adding a second validator invites an obvious objection — why not just call that
one? And a subtler risk: a runtime validator that grows toward feature parity
becomes a second implementation of identity derivation, and two
implementations of identity can disagree.

## Decision

The two checks answer different questions, run in different places, and stay
strictly separated.

**The producer's check** (`generate_registry.py --check`) asks: *is the
committed registry what the generator would produce from this corpus?* It needs
the corpus, the ledgers, the overrides and PyYAML.

**The consumer's check** (`pae validate-registry`) asks: *is this checkout's
registry safe for the Engine to serve from?* It takes the registry as given.

The consumer's check exists because a consumer may hold a checkout the
generator never ran in: a shallow clone, an export, a vendored copy, a registry
regenerated by a newer producer. Telling that user to run the producer's
toolchain to find out whether their registry is trustworthy defeats the purpose
of shipping a zero-dependency runtime.

It validates exactly the assumptions the Engine makes when serving: JSONL
parses; schemas are supported; required runtime fields exist; UID, public-ID
and alias shapes are valid and unique; aliases are disjoint from live public
IDs; relationship edges that name resources resolve to records; live source
paths are lexically safe and stay inside the root when resolved; those files
exist, are regular, and carry a verifiable checksum; and the summary agrees
with the records it summarizes. With `--verify-checksums` it hashes every live
source.

It **never** discovers the corpus, classifies kinds, derives UIDs, verifies the
identity freeze, applies overrides, migrates ledgers, parses techniques or
regenerates anything. A test asserts this against the module's executable code
— not its prose, which necessarily names the things it avoids.

Failures are **collected, not fatal on first sight**, and the command exits 9.
An agent told about one problem at a time fixes it and re-runs, four times.

One thing does stop the run: an unsupported record `schema_version` raises
incompatible-registry (exit 8) rather than accumulating findings, because past
that boundary the validator cannot name the fields it is checking.

## Consequences

- A consumer can establish trust in a registry without the producer's
  toolchain, its dependencies, or the corpus.
- There is exactly one implementation of identity derivation, and it is the
  generator's.
- The two checks can legitimately disagree — a checkout can hold a registry
  that is internally consistent and safe to serve but is not what the current
  generator would emit. That is information, not a bug.
- Exit 9 is reserved for runtime registry validation, distinct from exit 8
  (contract unsupported) and exit 7 (one file's integrity).
