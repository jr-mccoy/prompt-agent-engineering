# MP-05: Extended Thinking Documentation

## Category
Meta-Prompting (MP)

## Description
Extended Thinking Documentation is a meta-prompting technique that embeds system-level reasoning blocks explaining WHY a workflow is structured a certain way, documenting design rationale for complex multi-agent orchestrations. Unlike Chain of Thought (RT-01) which focuses on task execution reasoning, this technique preserves architectural design decisions, workflow sequencing rationale, and system-level trade-offs for long-term maintainability.

## When to Use

Use Extended Thinking Documentation when:

1. **Complex Multi-Agent Workflows**: Orchestrating multiple specialized agents with non-obvious sequencing
2. **Maintainable AI Systems**: Building prompts/workflows that will be modified months or years later
3. **Critical Decision Points**: Workflow contains important architectural choices that aren't self-evident
4. **Team Handoffs**: Workflows will be maintained by different people over time
5. **Production Systems**: Long-running AI systems requiring understanding of "why" to prevent breaking changes
6. **Training Materials**: Teaching others about orchestration design patterns

## Pattern

### Structural Template

```markdown
[Extended thinking: This workflow is designed to {PRIMARY_GOAL}. It follows
{KEY_PRINCIPLE_1} and {KEY_PRINCIPLE_2} to ensure {DESIRED_OUTCOME}.

The workflow is structured in {N} phases:
- Phase 1: {PHASE_NAME} - {RATIONALE}
- Phase 2: {PHASE_NAME} - {RATIONALE}
...

Key design decisions:
1. {DECISION}: We chose {APPROACH} over {ALTERNATIVE} because {REASONING}
2. {DECISION}: {APPROACH} is required to prevent {FAILURE_MODE}

Sequencing rationale:
- {STEP_A} must precede {STEP_B} because {DEPENDENCY_REASON}
- {STEP_C} and {STEP_D} can run in parallel because {INDEPENDENCE_REASON}

This design prevents {COMMON_FAILURE} and enables {BENEFIT}.]

## Workflow Implementation

{ACTUAL WORKFLOW STEPS}
```

### Placement Options

**Option 1: Workflow Header** (Recommended for orchestration commands)
```markdown
# Feature Development Workflow

[Extended thinking: Comprehensive rationale here...]

## Phase 1: Architecture
{steps}
```

**Option 2: Critical Decision Points**
```markdown
## Phase 2: Parallel Implementation

[Extended thinking: We enable parallel execution here because the API contracts
from Phase 1 provide clear interfaces. Backend and Frontend teams can work
simultaneously without integration conflicts...]

### Track A: Backend Development
### Track B: Frontend Development
```

**Option 3: Inline Annotations**
```markdown
### Step 3: Security Validation
[Thinking: Security validation happens AFTER implementation but BEFORE deployment
because we want working code to test against, but we absolutely cannot deploy
vulnerable code to production. This checkpoint prevents the "move fast and break
security" anti-pattern.]
```

## Example

### Complete Working Example: Full-Stack Feature Orchestration

```markdown
# Full-Stack Feature Development Command

[Extended thinking: This workflow coordinates multiple specialized agents to deliver
a complete full-stack feature from architecture through deployment. It follows
API-first development principles, ensuring contract-driven development where the API
specification drives both backend implementation and frontend consumption.

The architecture-first approach prevents integration issues that plague ad-hoc
development. By establishing database schemas, API contracts, and component
architectures BEFORE implementation begins, we enable:
1. Parallel development without merge conflicts
2. Clear accountability (each agent has explicit inputs/outputs)
3. Integration testing against known contracts
4. Easier debugging (contract violations are immediately obvious)

Key design decisions:
1. Database schema FIRST: We design the database before the API because the data
   model constrains what the API can efficiently provide. Retrofitting database
   design to match an API leads to performance problems.

2. API contracts BEFORE implementation: We use OpenAPI/GraphQL schemas as
   executable contracts. Both backend and frontend teams work from the same
   specification, preventing "it works on my machine" integration failures.

3. Security review BEFORE deployment: Security is a quality gate, not optional.
   We review after implementation (so there's working code to test) but before
   deployment (so vulnerabilities never reach production).

Sequencing rationale:
- Database → Backend API → Frontend: Data model constrains API design, API
  contract constrains frontend implementation. Reversing this order causes rework.

- Parallel tracks AFTER architecture: Backend, frontend, and additional database
  work can run simultaneously once contracts are established.

- Integration testing AFTER parallel tracks: We need all components complete
  before testing their interactions.

This design prevents the "big bang integration" anti-pattern where components
built in isolation fail when combined. It also prevents premature optimization
(security/performance tuning before the feature works) and premature deployment
(rushing to production before quality gates).]

## Phase 1: Architecture & Design Foundation

### 1. Database Architecture Design
**Agent:** database-architect
**Context:** Business requirements, expected data volume, access patterns
**Output:** Entity relationship diagrams, table schemas, migration scripts, indexing strategy

### 2. Backend Service Architecture
**Agent:** backend-architect
**Context:** Database schema from step 1, non-functional requirements (performance, scale)
**Output:** API specifications (OpenAPI/GraphQL), authentication flows, service boundaries

### 3. Frontend Architecture
**Agent:** frontend-developer (architecture focus)
**Context:** API contracts from step 2, UI/UX requirements
**Output:** Component hierarchy, state management approach, routing structure

## Phase 2: Parallel Implementation

[Extended thinking: These tasks run simultaneously because Phase 1 established
clear contracts. Each track has explicit inputs (the contracts) and outputs
(working implementations conforming to contracts). The convergence point is
integration testing where we verify the contracts were implemented correctly.]

### Track A: Backend Service Implementation
**Agent:** python-pro / nodejs-expert / golang-pro (based on tech stack)
**Context:** API specifications from Phase 1
**Output:** Working backend service with unit tests, API endpoints implemented

### Track B: Frontend Implementation
**Agent:** frontend-developer
**Context:** API contracts from Phase 1
**Output:** UI components, API integration, client-side routing, state management

### Track C: Database Implementation
**Agent:** database-architect
**Context:** Schema from Phase 1
**Output:** Migrations executed, seed data loaded, indexes created

**Coordination Note:** All tracks must complete before proceeding to Phase 3.

## Phase 3: Integration & Quality Gates

### 4. Integration Testing
**Agent:** test-automator
**Context:** All implementations from Phase 2
**Output:** Integration test suite, end-to-end test scenarios, test results

### 5. Security Audit
**Agent:** security-auditor
**Context:** Complete implementation, test results
**Output:** Security scan results, vulnerability report, remediation recommendations

[Extended thinking: Security happens here (not earlier) because we need working
code to audit. It happens here (not later) because we never deploy vulnerable code.]

### 6. Performance Validation
**Agent:** performance-engineer
**Context:** Working system, expected load characteristics
**Output:** Performance test results, bottleneck analysis, optimization recommendations

## Phase 4: Deployment

### 7. Deployment Orchestration
**Agent:** deployment-engineer
**Context:** Quality gates passed, deployment target (staging/production)
**Output:** Deployed application, smoke test results, rollback plan

### 8. Observability Setup
**Agent:** observability-engineer
**Context:** Deployed application, critical user journeys
**Output:** Monitoring dashboards, alerting rules, logging configuration

## Validation & Handoff

### Success Criteria
- All quality gates passed (tests, security, performance)
- Documentation complete (API docs, runbooks, architecture decision records)
- Monitoring and alerting operational
- Team trained on new feature

[Extended thinking: Success isn't just "code works" - it's "team can operate and
evolve this feature." That requires documentation, monitoring, and knowledge transfer.]
```

## Variations

### Variation 1: Condensed Format for Simpler Workflows

For less complex workflows, use abbreviated thinking blocks:

```markdown
# Code Review Workflow

[Thinking: Review happens in three passes (structure → logic → edge cases) to
prevent cognitive overload. Checking everything at once misses subtle bugs.]

## Pass 1: Structural Review
{steps}
```

### Variation 2: Decision Trees with Rationale

When workflows have multiple paths:

```markdown
## Deployment Decision Point

[Extended thinking: Deployment strategy depends on change risk and user impact.
High-risk changes use blue-green deployment for instant rollback. Low-risk changes
use rolling deployment for resource efficiency. Risk is determined by: scope of
change, test coverage, and blast radius.]

**IF** high-risk change (breaking changes, database migrations, auth changes):
  → Use blue-green deployment

**ELIF** medium-risk change (new features, significant refactors):
  → Use canary deployment (5% → 20% → 100%)

**ELSE** low-risk change (bug fixes, content updates):
  → Use rolling deployment
```

### Variation 3: Anti-Pattern Documentation

Explicitly document what NOT to do:

```markdown
[Extended thinking: This workflow enforces architecture-first development.

ANTI-PATTERN: "Just start coding and figure it out later"
- Leads to: Integration conflicts, rework, technical debt

ANTI-PATTERN: "Skip tests, we'll add them later"
- Leads to: Untested code in production, regression bugs

ANTI-PATTERN: "Security review after deployment"
- Leads to: Vulnerabilities in production, emergency patches

This workflow prevents these failures through enforced quality gates.]
```

### Variation 4: Scalability Rationale

For production systems that will evolve:

```markdown
[Extended thinking: This orchestration is designed to scale from 1 feature to
100 features without modification. Each agent is stateless and parameterized.
Configuration (tech stack, deployment target, testing depth) is injected, not
hardcoded. This means the same workflow serves React/Django/AWS and Vue/Rails/GCP
projects without duplication.]
```

## Combination Patterns

Extended Thinking Documentation works exceptionally well with:

### 1. **AG-13 (Parallel-Converge Orchestration)**
Use extended thinking to explain WHY certain steps can run in parallel and WHERE convergence points are required:

```markdown
[Extended thinking: Backend and frontend tracks run in parallel because API
contracts from Phase 1 eliminate dependencies. They MUST converge at integration
testing because we need both components to validate the contract implementation.]
```

### 2. **DS-13 (Architecture-First Enforcement)**
Document WHY architecture must precede implementation:

```markdown
[Extended thinking: Architecture-first isn't bureaucracy - it's risk mitigation.
Designing APIs before implementation prevents the "works in isolation, fails in
integration" pattern that costs 10x more to fix than upfront design.]
```

### 3. **AG-14 (Cost-Aware Agent Orchestration)**
Explain model assignment rationale:

```markdown
[Extended thinking: We use Opus for architecture review (step 1) because
architectural mistakes are expensive to fix later. We use Haiku for syntax
checking (step 7) because it's 60x cheaper and mistakes are easily caught in
testing. Model tiering isn't about saving money - it's about allocating
expensive reasoning to high-value decisions.]
```

### 4. **CM-05 (Progressive Context Accumulation)**
Document how context flows through workflow stages:

```markdown
[Extended thinking: Each step consumes the previous step's output as context.
This explicit chaining prevents context loss in long workflows and makes
dependencies visible. If step 5 fails, we know exactly which prior context
it was missing.]
```

### 5. **QA-06 (Constitutional AI for Prompts)**
Use extended thinking in the critique phase:

```markdown
## Critique Phase

[Extended thinking: We critique against 5 constitutional principles because
ad-hoc review misses systematic issues. Each principle targets a different
failure mode: clarity (misinterpretation), completeness (edge cases),
consistency (contradictions), conciseness (cognitive overload), correctness
(wrong outcomes).]
```

## Pitfalls

### Pitfall 1: Over-Documentation
**Problem:** Extended thinking blocks become essays that nobody reads

**Example (BAD):**
```markdown
[Extended thinking: This workflow implements a comprehensive multi-agent
orchestration system utilizing advanced software engineering principles
including separation of concerns, dependency injection, contract-driven
development, test-driven development, continuous integration, continuous
deployment, observability-driven development, and security-first architecture.
The theoretical foundations draw from distributed systems theory, specifically
the CAP theorem, eventual consistency models, and fault-tolerant computing...
(continues for 500 more words)]
```

**Solution:** Keep it focused - explain WHAT decision was made, WHY, and what it prevents. Maximum 200-300 words per block.

**Example (GOOD):**
```markdown
[Extended thinking: API contracts first because data model constrains API
design, API constrains frontend. Reversing this order causes expensive rework.
Security review before deployment (not after) because we never deploy vulnerable
code. Parallel tracks after contracts because clear interfaces eliminate
integration conflicts.]
```

### Pitfall 2: Stating the Obvious
**Problem:** Documenting what's already clear from the workflow structure

**Example (BAD):**
```markdown
[Extended thinking: Step 1 runs first, then step 2 runs second, then step 3
runs third. This is a sequential workflow where each step happens in order.]
```

**Solution:** Only document non-obvious rationale. If sequencing is obvious, skip it.

### Pitfall 3: Missing the "Why"
**Problem:** Describing WHAT the workflow does instead of WHY it's designed that way

**Example (BAD):**
```markdown
[Extended thinking: This workflow has 7 steps. The first step designs the
database. The second step designs the API. The third step implements the backend...]
```

**Solution:** Focus on design decisions and trade-offs, not step descriptions.

**Example (GOOD):**
```markdown
[Extended thinking: Database design precedes API design because the data model
constrains what the API can efficiently provide. Designing the API first leads
to databases that can't support the promised API contracts, requiring expensive
refactoring.]
```

### Pitfall 4: Outdated Documentation
**Problem:** Workflow changes but extended thinking doesn't update

**Example:**
```markdown
[Extended thinking: We use Opus for all steps because quality is critical...]

## Step 7: Syntax Checking
**Model:** Haiku  <!-- Workflow changed but thinking didn't! -->
```

**Solution:** Treat extended thinking as first-class documentation. When workflow changes, update the thinking.

### Pitfall 5: Confusing Extended Thinking with Execution Thinking
**Problem:** Mixing workflow design rationale (extended thinking) with task execution reasoning (chain of thought)

**Example (CONFUSED):**
```markdown
[Extended thinking: To solve this math problem, first I'll add 5 and 3, then
multiply by 2...]  <!-- This is Chain of Thought, not Extended Thinking -->
```

**Solution:** Extended Thinking = WHY the workflow/system is designed this way. Chain of Thought = HOW to execute a specific task.

### Pitfall 6: No Failure Mode Analysis
**Problem:** Explaining what the workflow does without explaining what it prevents

**Example (INCOMPLETE):**
```markdown
[Extended thinking: We review code in three passes for thoroughness.]
```

**Solution:** Always include what failure modes this design prevents.

**Example (COMPLETE):**
```markdown
[Extended thinking: We review code in three passes (structure → logic → edge
cases) because single-pass review suffers from cognitive overload. Reviewers
checking everything simultaneously miss subtle logic bugs. Three-pass review
prevents the "looks good to me" rubber-stamp pattern.]
```

---

## Summary

Extended Thinking Documentation (MP-05) is a critical technique for building maintainable multi-agent orchestrations. By documenting the WHY behind workflow design (not just the WHAT), it prevents future modifications from breaking carefully-designed systems. Use it for any complex workflow that will be maintained over time, especially those involving multiple agents, non-obvious sequencing, or critical design trade-offs.

**Key Takeaway:** If someone might ask "Why is this workflow structured this way?" in 6 months, document the answer now with Extended Thinking Documentation.
