# CM-05: Progressive Context Accumulation

## Category
Context Management (CM)

## Description
Progressive Context Accumulation is a context management technique that explicitly chains context through multi-step workflows, where each phase's output becomes the next phase's input context with transparent dependency tracking. This prevents context loss in long-running workflows by making information handoffs explicit and ensuring each agent receives exactly the context it needs from previous steps.

## When to Use

Use Progressive Context Accumulation when:

1. **Multi-Step Workflows**: Workflows with 3+ sequential phases where later steps depend on earlier outputs
2. **Long-Running Projects**: Projects spanning multiple sessions where context must persist and evolve
3. **Multi-Agent Orchestration**: Different specialized agents handle different phases
4. **Complex Dependencies**: Clear information handoffs required between workflow stages
5. **Context Preservation**: Risk of losing critical information between workflow steps
6. **Explicit Traceability**: Need to trace which inputs influenced which outputs

## Variations

### Variation 1: Branching Context Flow

When multiple parallel tracks exist:

```markdown
## Phase 2: Parallel Tracks

### Track A: Backend Implementation
**Context Input:**
- From Phase 1: Database schema, query patterns

**Context Output:**
- API implementation
- Passes to: Phase 3 (Integration Testing)

### Track B: Frontend Implementation
**Context Input:**
- From Phase 1: Database schema (for data modeling)
- From Phase 2 Design: API contracts (separate from Track A implementation)

**Context Output:**
- UI components
- Passes to: Phase 3 (Integration Testing)

## Phase 3: Integration Testing
**Context Input:**
- From Track A: Backend implementation ← Convergence point
- From Track B: Frontend implementation ← Convergence point
- From Phase 1: Acceptance criteria
```

### Variation 2: Condensed Format for Simpler Workflows

```markdown
## Step 1: Analyze Requirements
**Output:** User stories, acceptance criteria

## Step 2: Design Solution
**Input:** User stories from Step 1
**Output:** Architecture diagrams, API specs

## Step 3: Implement
**Input:** API specs from Step 2
**Output:** Working code, unit tests
```

### Variation 3: Context Accumulation with Validation Gates

```markdown
## Phase 1: Design
**Output:** Architecture document

**Validation Gate:** Architecture review must approve before Phase 2
- [ ] Scalability concerns addressed
- [ ] Security reviewed
- ✅ Approved by: @senior-architect

## Phase 2: Implementation
**Input:** Approved architecture from Phase 1 ← Validated context
**Output:** Working code
```

### Variation 4: Explicit Context Loss Prevention

```markdown
## Phase 3: Frontend Development

### Context Required (DO NOT PROCEED WITHOUT):
- ✅ API specification from Phase 2 (openapi.yaml)
- ✅ Authentication flow from Phase 2 (auth_flow.md)
- ❌ Database schema (NOT NEEDED - abstracted by API)

### Common Pitfall Prevention:
⚠️ Do NOT access database directly from frontend
⚠️ Do NOT guess at API structure - use OpenAPI spec from Phase 2
```

## Pitfalls

### Pitfall 1: Context Duplication
**Problem:** Passing entire context history to every phase, causing token bloat

**Example (BAD):**
```markdown
## Phase 5
**Input:**
- Everything from Phase 1 (10K tokens)
- Everything from Phase 2 (8K tokens)
- Everything from Phase 3 (12K tokens)
- Everything from Phase 4 (6K tokens)
**Total:** 36K tokens (context limit exceeded!)
```

**Solution:** Pass only relevant context from previous phases

**Example (GOOD):**
```markdown
## Phase 5: Deployment
**Input:**
- Deployment artifacts from Phase 4 (500 tokens)
- Production config requirements from Phase 1 (200 tokens)
**Total:** 700 tokens
**Archived:** Phases 2-3 (not needed for deployment)
```

### Pitfall 2: Missing Explicit Dependencies
**Problem:** Implicit dependencies that break when workflow changes

**Example (BAD):**
```markdown
## Phase 2: Implementation
**Input:** Requirements
**Output:** Code

## Phase 3: Testing
**Input:** Code
```
*Question: Where are the API specs? Who defined them?*

**Solution:** Make every dependency explicit

**Example (GOOD):**
```markdown
## Phase 1.5: API Design (added)
**Input:** Requirements from Phase 1
**Output:** API specification

## Phase 2: Implementation
**Input:** Requirements from Phase 1, API spec from Phase 1.5
**Output:** Code conforming to API spec
```

### Pitfall 3: Context Loss at Convergence Points
**Problem:** Parallel tracks don't preserve their outputs for convergence phase

**Example (BAD):**
```markdown
## Phase 2: Parallel Tracks
Track A: Backend → produces API
Track B: Frontend → produces UI

## Phase 3: Integration Testing
**Input:** ??? (tracks didn't document what they pass forward)
```

**Solution:** Explicit output handoffs from all parallel tracks

**Example (GOOD):**
```markdown
## Phase 2: Parallel Tracks
Track A: Backend
**Output → Phase 3:** Running API service, API spec, Postman collection

Track B: Frontend
**Output → Phase 3:** Built UI bundle, component tests, user flow documentation

## Phase 3: Integration Testing
**Receives:**
- Backend API + spec from Track A
- Frontend UI + tests from Track B
```

### Pitfall 4: Undocumented Format Expectations
**Problem:** Phase N produces output in format X, Phase N+1 expects format Y

**Example (BAD):**
```markdown
## Phase 1: Data Collection
**Output:** User data

## Phase 2: Analysis
**Input:** User data from Phase 1
**ERROR:** Phase 1 output CSV, Phase 2 expected JSON!
```

**Solution:** Document expected formats explicitly

**Example (GOOD):**
```markdown
## Phase 1: Data Collection
**Output:** User data
**Format:** CSV file with columns: user_id, name, email, signup_date

## Phase 2: Analysis
**Input:** User data from Phase 1 (CSV format)
**Format Requirement:** CSV with required columns: user_id, signup_date
```

### Pitfall 5: No Validation Between Phases
**Problem:** Phase N produces incomplete output, Phase N+1 fails silently

**Example (BAD):**
```markdown
## Phase 1: Requirements
**Output:** Requirements doc

## Phase 2: Design
**Input:** Requirements from Phase 1
**ERROR:** Requirements missing critical acceptance criteria!
```

**Solution:** Add validation criteria between phases

**Example (GOOD):**
```markdown
## Phase 1: Requirements
**Output:** Requirements doc
**Validation Before Phase 2:**
- [x] Functional requirements documented
- [x] Non-functional requirements documented
- [x] Acceptance criteria defined
- [x] Stakeholder approval received

**✅ Phase 1 Complete - Proceed to Phase 2**

## Phase 2: Design
**Input:** Validated requirements from Phase 1
```

## Summary

Progressive Context Accumulation (CM-05) prevents context loss in multi-step workflows by making information handoffs explicit. Instead of assuming agents have the context they need, this technique explicitly documents what each phase receives as input and what it produces as output. This transparency prevents integration failures and makes workflows easier to debug and maintain.

**Key Takeaway:** If your workflow has 3+ sequential phases where later steps depend on earlier outputs, use Progressive Context Accumulation to make dependencies explicit and prevent context loss.
