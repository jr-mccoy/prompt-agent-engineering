# DS-13: Architecture-First Enforcement

## Category
Domain-Specific (DS)

## Description
Architecture-First Enforcement is a workflow design technique that enforces architectural decisions before implementation by sequencing phases and requiring specific outputs as dependencies. By making architecture a blocking prerequisite for implementation, this technique prevents ad-hoc development that leads to integration problems, forces upfront design thinking, and enables parallel development with clear interfaces.

## When to Use

Use Architecture-First Enforcement when:

1. **Large Features**: Complex features where ad-hoc development leads to integration problems
2. **API-First Development**: Projects requiring contract-driven development where API specifications drive implementation
3. **Distributed Teams**: Multiple teams working on different components that must integrate seamlessly
4. **Preventing Integration Failures**: History of "works in isolation, fails in integration" problems
5. **Enforcing Architectural Discipline**: Teams needing structured approach to prevent shortcuts
6. **Parallel Development**: Enabling frontend and backend teams to work simultaneously without conflicts

4. **Workflow Sequencing:** Architecture phase numbered before implementation phase
```

**Table Schemas:**
```sql
-- carts table
CREATE TABLE carts (
    cart_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES users(user_id) NULL,  -- NULL for guest carts
    session_id VARCHAR(255) UNIQUE,  -- For guest cart identification
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    expires_at TIMESTAMP,  -- Guest carts expire after 7 days
    status VARCHAR(20) DEFAULT 'active',  -- active, abandoned, converted
    INDEX idx_user_carts (user_id, status),
    INDEX idx_session (session_id),
    INDEX idx_expires (expires_at, status)
);

-- cart_items table
CREATE TABLE cart_items (
    item_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    cart_id UUID REFERENCES carts(cart_id) ON DELETE CASCADE,
    product_id UUID REFERENCES products(product_id),
    quantity INTEGER NOT NULL CHECK (quantity > 0),
    added_at TIMESTAMP DEFAULT NOW(),
    UNIQUE (cart_id, product_id),  -- Prevent duplicate products in cart
    INDEX idx_cart_items (cart_id)
);

-- inventory table (real-time stock tracking)
CREATE TABLE inventory (
    inventory_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    product_id UUID REFERENCES products(product_id),
    warehouse_id UUID REFERENCES warehouses(warehouse_id),
    quantity_available INTEGER NOT NULL DEFAULT 0,
    quantity_reserved INTEGER NOT NULL DEFAULT 0,  -- In carts but not purchased
    updated_at TIMESTAMP DEFAULT NOW(),
    UNIQUE (product_id, warehouse_id),
    INDEX idx_product_stock (product_id)
);
```

**Data Access Patterns:**
```markdown
1. Get user's active cart:
   SELECT * FROM carts WHERE user_id = ? AND status = 'active'

2. Get cart items with inventory check:
   SELECT ci.*, p.name, p.price, i.quantity_available
   FROM cart_items ci
   JOIN products p ON ci.product_id = p.product_id
   LEFT JOIN inventory i ON p.product_id = i.product_id
   WHERE ci.cart_id = ?

3. Reserve inventory when adding to cart:
   UPDATE inventory
   SET quantity_reserved = quantity_reserved + ?
   WHERE product_id = ? AND warehouse_id = ?
   AND quantity_available >= ?  -- Ensure stock available
```

**Authentication Flow:**
```markdown
## Authenticated Users
1. User logs in → Receives JWT token
2. JWT token included in `Authorization: Bearer {token}` header
3. Backend validates token, extracts user_id
4. Queries: `SELECT * FROM carts WHERE user_id = ? AND status = 'active'`

## Guest Users
1. User visits site → Backend generates session_id (UUID)
2. Session cookie set: `Set-Cookie: session_id={uuid}; HttpOnly; Secure; SameSite=Strict`
3. Backend validates session_id from cookie
4. Queries: `SELECT * FROM carts WHERE session_id = ? AND status = 'active'`

## Guest → Authenticated User Migration
1. User logs in after adding items as guest
2. Backend merges guest cart into user's account:
   ```sql
   UPDATE carts SET user_id = ?, session_id = NULL
   WHERE session_id = ? AND status = 'active'
   ```
```

**API Integration Layer:**
```typescript
// API client matching OpenAPI spec from Step 1.2
class CartAPI {
  private baseURL = '/api/v1';
  private authToken: string | null = null;

  setAuthToken(token: string) {
    this.authToken = token;
  }

  // GET /api/v1/cart
  async getCart(): Promise<Cart> {
    const response = await fetch(`${this.baseURL}/cart`, {
      method: 'GET',
      headers: this.getHeaders(),
      credentials: 'include'  // Include session cookie for guest users
    });

    if (!response.ok) {
      throw new APIError(response.status, await response.json());
    }

    return await response.json();
  }

  // POST /api/v1/cart/items
  async addItem(productId: string, quantity: number): Promise<CartItem> {
    const response = await fetch(`${this.baseURL}/cart/items`, {
      method: 'POST',
      headers: this.getHeaders(),
      credentials: 'include',
      body: JSON.stringify({ product_id: productId, quantity })
    });

    if (response.status === 409) {
      // Insufficient inventory - extract available quantity
      const error = await response.json();
      throw new InsufficientInventoryError(
        error.available_quantity,
        error.requested_quantity
      );
    }

    if (!response.ok) {
      throw new APIError(response.status, await response.json());
    }

    return await response.json();
  }

  // PATCH /api/v1/cart/items/{item_id}
  async updateQuantity(itemId: string, quantity: number): Promise<void> {
    const response = await fetch(`${this.baseURL}/cart/items/${itemId}`, {
      method: 'PATCH',
      headers: this.getHeaders(),
      credentials: 'include',
      body: JSON.stringify({ quantity })
    });

    if (response.status === 409) {
      const error = await response.json();
      throw new InsufficientInventoryError(error.available_quantity, quantity);
    }

    if (!response.ok) {
      throw new APIError(response.status, await response.json());
    }
  }

  // DELETE /api/v1/cart/items/{item_id}
  async removeItem(itemId: string): Promise<void> {
    const response = await fetch(`${this.baseURL}/cart/items/${itemId}`, {
      method: 'DELETE',
      headers: this.getHeaders(),
      credentials: 'include'
    });

    if (!response.ok && response.status !== 404) {
      throw new APIError(response.status, await response.json());
    }
  }

  private getHeaders(): HeadersInit {
    const headers: HeadersInit = {
      'Content-Type': 'application/json'
    };

    if (this.authToken) {
      headers['Authorization'] = `Bearer ${this.authToken}`;
    }

    return headers;
  }
}
```

class APIError extends Error {

class InsufficientInventoryError extends Error {

// Optimistic add to cart
const addItemOptimistically = async (productId: string, quantity: number) => {
  // 1. Optimistically update UI (instant feedback)
  const optimisticItem = {
    item_id: `temp-${Date.now()}`,  // Temporary ID
    product_id: productId,
    quantity,
    // ... other fields
  };

  setCart(prev => ({
    ...prev,
    items: [...prev.items, optimisticItem],
    total_items: prev.total_items + quantity
  }));

  try {
    // 2. Call API
    const actualItem = await cartAPI.addItem(productId, quantity);

    // 3. Replace optimistic item with real item
    setCart(prev => ({
      ...prev,
      items: prev.items.map(item =>
        item.item_id === optimisticItem.item_id ? actualItem : item
      )
    }));
  } catch (error) {
    // 4. Rollback on error
    setCart(prev => ({
      ...prev,
      items: prev.items.filter(item => item.item_id !== optimisticItem.item_id),
      total_items: prev.total_items - quantity
    }));

    // Show error to user
    showError(error);
  }
};

  });
});

## Pitfalls

### Pitfall 1: Architecture Without Enforcement

**Problem:** Architecture documented but not enforced; teams skip ahead to implementation

**Example (BAD):**
```markdown
## Phase 1: Architecture
(Architecture documented but...)

## Phase 2: Implementation
**Backend Team:** "We'll just start coding, the architecture is just a guideline"
**Frontend Team:** "We can't wait for backend, we'll guess at the API structure"

**Result:** Integration failures, rework
```

**Solution:** Explicit validation gates that block progress

**Example (GOOD):**
```markdown
## Phase 1: Architecture
(Architecture documented)

**🚦 VALIDATION GATE (BLOCKS PHASE 2):**
- [ ] Architecture review approved
- [ ] All teams signed off
- [ ] Contracts validated (OpenAPI spec passes validation)

**Status:** ⏸️ Phase 2 BLOCKED until gate passes

## Phase 2: Implementation
**Cannot start until Phase 1 gate passes**
```

### Pitfall 2: Over-Architecting Small Features

**Problem:** Applying heavyweight architecture process to simple features

**Example (BAD):**
```markdown
Feature: Add "favorite" button to posts

## Phase 1: Architecture (2 weeks)
- Database schema: 50-page design document
- API contracts: Comprehensive OpenAPI spec
- Frontend architecture: Full component hierarchy
- Architecture review: 3 meetings, 15 stakeholders

**Result:** 2 weeks of architecture for 2-hour implementation
```

**Solution:** Scale architecture rigor to feature complexity

**Example (GOOD):**
```markdown
Feature: Add "favorite" button to posts (simple feature)

## Quick Architecture (30 minutes)
- Database: Add `favorites` table (user_id, post_id)
- API: POST /posts/{id}/favorite, DELETE /posts/{id}/favorite
- Frontend: FavoriteButton component

**Review:** Quick Slack approval from tech lead

## Implementation (2 hours)
(Implement per simple contracts above)
```

### Pitfall 3: Architecture-Implementation Gap

**Problem:** Architecture designed by one team, implemented by different team without context

**Example (BAD):**
```markdown
## Phase 1: Architecture
**Architect:** Designs complex API with 20 endpoints, intricate error handling

## Phase 2: Implementation
**Developer:** "I don't understand why the architecture is this way, I'll simplify it"
**Result:** Implementation doesn't match architecture, integration breaks
```

**Solution:** Include implementers in architecture phase

**Example (GOOD):**
```markdown
## Phase 1: Architecture

**Participants:**
- @alice (architect) - Proposes design
- @bob (backend implementer) - Reviews feasibility
- @charlie (frontend implementer) - Reviews usability

**Collaborative design ensures implementability**
```

### Pitfall 4: No Contract Testing

**Problem:** Architecture defined but not validated; implementations deviate silently

**Example (BAD):**
```markdown
## Architecture: API returns 409 on insufficient inventory

## Backend Implementation:
return Response({"error": "Out of stock"}, status=200)  # Wrong status!

## Frontend Implementation:
if (response.status === 409) { ... }  # Never triggers

**Result:** Error handling broken, no one noticed until production
```

**Solution:** Contract testing validates implementations match architecture

**Example (GOOD):**
```typescript
// Contract test: Backend must match OpenAPI spec
test('POST /cart/items returns 409 on insufficient inventory', async () => {
  const response = await api.addItem(productId, quantity);

  expect(response.status).toBe(409);  // Per OpenAPI spec
  expect(response.data).toMatchSchema({  // Validate schema
    error: 'string',
    available_quantity: 'number',
    requested_quantity: 'number'
  });
});
```

### Pitfall 5: Architecture Never Updates

**Problem:** Initial architecture becomes outdated but process prevents evolution

**Example (BAD):**
```markdown
## Year 1: Architecture-First Enforced
- Database schema locked in
- API contracts frozen

## Year 3: New Requirements
**Team:** "We need to add real-time features but architecture doesn't support it"
**Manager:** "Architecture is locked, we can't change it"

**Result:** System can't evolve, technical debt accumulates
```

**Solution:** Architecture versioning with migration path

**Example (GOOD):**
```markdown
## Architecture V1 (Current Production)
- REST API
- Polling for updates

## Architecture V2 (Proposed)
- REST API (backward compatible)
- WebSocket for real-time updates (new)

**Migration Path:**
1. Deploy V2 alongside V1 (both supported)
2. Migrate clients gradually to WebSocket
3. Deprecate polling after 6 months
```
