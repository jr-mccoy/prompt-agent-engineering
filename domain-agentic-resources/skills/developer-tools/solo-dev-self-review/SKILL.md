# Solo Dev Self-Review

Structured self-code-review workflow for developers who merge their own code. Replaces the external reviewer with systematic techniques that overcome the "author's blindness" problem — where your brain auto-corrects bugs because you know what the code is supposed to do.

## Purpose

Solo developers write and merge their own code with no external review. This is the single biggest quality gap in solo development — not architecture, not testing, but the absence of a second pair of eyes. Research shows that code review catches 60-90% of defects before they reach production. This skill provides a structured process that catches the majority of issues a reviewer would find, using techniques specifically designed to break the author's familiarity with their own code.

## When to Use This Skill

Use this skill when you need to:
- Review your own code before merging a feature branch
- Do a quality pass after a vibe coding session
- Review changes before a release
- Validate a bug fix before deploying
- Check code you wrote more than a week ago

## When NOT to Use This Skill

Do NOT use this skill when:
- You have access to a human reviewer (use them instead)
- The change is purely generated by tooling (auto-formatting, dependency updates)
- You are in the middle of a vibe coding session (review after, not during)
- The change is a revert to a known-good state

## Prerequisites

- Changes committed to a branch (not uncommitted work)
- Ability to view git diffs
- 15-30 minutes of focused time (no multi-tasking during review)

## Step 1: Pre-Review Ritual (2 minutes)

### 1.1 Break Context

Do NOT review code immediately after writing it. Your brain is still in "author mode" and will skip over issues.

**Minimum breaks:**
- Small change (<50 lines): 10-minute break
- Medium change (50-200 lines): 30-minute break or next morning
- Large change (200+ lines): Next day

If you cannot wait, switch to a completely different task for 10 minutes (check email, walk, stretch).

### 1.2 Set Review Intent

Before looking at any code, write down what the change is supposed to do in one sentence:

```
"This change adds: ___________"
"This change fixes: ___________"
"This change refactors: ___________"
```

This primes your brain to notice code that doesn't serve this purpose.

## Step 2: Overview First (3 minutes)

### 2.1 Stats Review

```bash
# What changed — file count and size
git diff --stat main..HEAD

# How many lines total
git diff main..HEAD --shortstat
```

Check:
- Are these the files you expected to change?
- Are there any surprise files? (generated files, config changes you forgot about)
- Is the change size proportional to the feature? (500 lines for a one-line fix = red flag)

### 2.2 Commit History

```bash
# Review your commits
git log --oneline main..HEAD
```

Check:
- Do commit messages explain "why", not "what"?
- Are commits atomic (one logical change per commit)?
- Any "WIP" or "fix" commits that should be squashed?

## Step 3: Diff Review (10-15 minutes)

### 3.1 Review Order

Review files in this order (not the order git shows them):

1. **Test files first** — Do the tests verify the right behavior?
2. **Interface/API changes** — Public methods, API contracts, data models
3. **Core logic** — The actual implementation
4. **Configuration/infrastructure** — Build files, configs, manifests
5. **Largest files last** — Your attention fades; save big files for when you're fresh (or review them first if you have the discipline)

### 3.2 The Checklist

For each file, check:

**Correctness:**
- [ ] Does this code do what the commit message says?
- [ ] Are there off-by-one errors in loops or ranges?
- [ ] Are null/undefined cases handled?
- [ ] Are return values checked (not silently ignored)?

**Error Handling:**
- [ ] What happens when this fails? (network, disk, invalid input)
- [ ] Are errors logged with enough context to debug later?
- [ ] Can the user recover from errors, or does the app just crash?

**Edge Cases:**
- [ ] Empty collections — does the code handle zero items?
- [ ] Missing data — what if an API field is null/absent?
- [ ] Concurrent access — can this be called from multiple threads?
- [ ] Large inputs — what if there are 10,000 items instead of 10?

**Security:**
- [ ] No hardcoded secrets (API keys, passwords, tokens)
- [ ] User input is validated before use
- [ ] No SQL/command injection vectors
- [ ] Sensitive data isn't logged

**Naming and Clarity:**
- [ ] Could a stranger understand this code in 6 months?
- [ ] Are variable names descriptive? (not `x`, `temp`, `data2`)
- [ ] Are there any misleading names? (function says "get" but modifies state)

### 3.3 The "Explain It" Test

For any complex logic, explain what it does out loud (or in a comment). If you struggle to explain it, it is too complex and should be simplified.

## Step 4: Perspective Switching (5 minutes)

This is the most powerful technique for solo review. Deliberately adopt a different perspective and re-scan the diff.

### 4.1 Perspectives to Try

Pick 1-2 perspectives per review (all of them every time is overkill):

**"New team member" perspective:**
- Could someone who has never seen this codebase understand the change?
- Are there implicit assumptions that should be documented?
- Does the code follow patterns already established in the project?

**"Attacker" perspective:**
- Can user input reach this code unsanitized?
- Can this code be abused to access data it shouldn't?
- What happens if someone sends malformed data?

**"User on bad network" perspective:**
- What if every API call takes 10 seconds?
- What if the API returns a 500 error?
- What if the device goes offline mid-operation?

**"Future you" perspective:**
- Will you understand why you made this choice in 3 months?
- Is there a simpler way to do this that you're avoiding because the current approach is already written?
- Are you creating tech debt that you'll be forced to address soon?

## Step 5: Verdict (2 minutes)

### 5.1 Ship Decision

After reviewing, pick one:

| Verdict | Criteria | Action |
|---------|----------|--------|
| **SHIP IT** | No issues found, or only minor style preferences | Merge immediately |
| **SHIP WITH NOTES** | Small issues that don't affect correctness | Merge, create follow-up tasks for the issues |
| **HOLD** | Correctness issues, security problems, or missing error handling | Fix before merging |

### 5.2 Document Findings

For anything you hold or note, write a brief summary:

```markdown
## Self-Review: [branch-name] — [date]
**Verdict:** SHIP WITH NOTES

**Issues Found:**
1. Missing error handling in `fetchUser()` — will crash on 404
2. Hardcoded timeout of 5000ms — should be configurable
3. No loading state shown during data fetch

**Follow-up Tasks:**
- [ ] Add error handling to network layer
- [ ] Extract timeout to config
- [ ] Add loading UI states
```

## Common Solo Dev Blind Spots

These are the issues most commonly missed when reviewing your own code. Scan for them explicitly:

| Blind Spot | What to Check |
|-----------|--------------|
| **Happy path only** | Did you only test the success case? What about failures? |
| **Hardcoded values** | URLs, timeouts, retry counts, feature flags buried in code |
| **Missing states** | Loading, empty, error — most UIs need all three |
| **Scope creep** | Did you change things unrelated to the feature? Revert them. |
| **Dead code** | Commented-out code, unused imports, unreachable branches |
| **Implicit dependencies** | Does this code assume something is initialized first? |
| **Resource leaks** | Opened but not closed: database cursors, streams, connections |
| **Race conditions** | Two coroutines modifying the same state? |

## Time-Boxing Guide

| Change Size | Max Review Time | Rationale |
|------------|-----------------|-----------|
| <20 lines | 5 minutes | Quick scan, checklist only |
| 20-100 lines | 15 minutes | Full checklist + one perspective |
| 100-300 lines | 25 minutes | Full checklist + two perspectives |
| 300+ lines | 30 minutes | If the review needs more time, the PR is too big. Split it. |

**Hard rule:** Never review for more than 30 minutes in one sitting. After 30 minutes, your ability to find issues drops sharply. Take a break and return.
