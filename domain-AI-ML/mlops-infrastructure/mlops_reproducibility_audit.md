# MLOps Reproducibility Audit

**Objective:** Audit an existing ML project across the five reproducibility axes — code, data, environment, seeds/determinism, and config — and return a ranked list of gaps with the specific consequence of each and a concrete fix, so that any reported result can be regenerated by someone else, later, on different hardware (within stated tolerance).

**When to Use:**
- A result cannot be reproduced — different numbers on re-run, or nobody can re-run it at all.
- Before trusting a model for promotion, audit, or publication.
- Inheriting a project/notebook and needing to know what is and isn't re-runnable.
- A regulated or high-stakes setting requires provable lineage.

**When NOT to Use:**
- To *design* tracking from scratch (use `mlops_experiment_tracking_setup.md`).
- To debug *why metrics look too good* — that is leakage, not reproducibility (use `mldata_data_leakage_detector.md`).

## Inputs / Context

Provide what you can; the audit degrades gracefully:
- **The result to reproduce** — the metric/model the user wants to regenerate, and where it was reported.
- **Code access** — repo, notebook, or scripts; whether the exact commit is known.
- **Data provenance** — how the training/eval data was produced; whether it is versioned/snapshotted.
- **Environment** — how dependencies are specified (requirements/lockfile/image), Python/CUDA versions, hardware.
- **Randomness** — whether seeds are set; any nondeterministic ops (GPU, parallelism, data shuffling).
- **Config** — how hyperparameters/paths are passed (hardcoded, CLI, config file, env vars).

## Constraints

**Must:**
- Assess all five axes (code, data, environment, seeds, config) and state, per axis, whether the gap is blocking or degrading.
- Anchor every gap to specific evidence in the project, not a generic checklist item.
- Define the acceptable reproduction tolerance up front (bit-exact vs metric-within-ε) — perfect determinism is often impossible on GPU.

**Must Not:**
- Demand bit-exact determinism where it is infeasible (e.g., nondeterministic CUDA kernels) without saying so.
- Assume a gap exists without checking; mark "unknown — needs check" distinctly from "confirmed gap."
- Conflate "the code runs" with "the result reproduces."

**Instructions:**

1. **Fix the target and tolerance.** State exactly which result must reproduce and what counts as success (bit-exact, or metric within ε). This anchors every gap to its actual consequence.

2. **Audit code reproducibility.** Is the exact commit known and clean (no uncommitted diff)? Are all entry points and steps in version control, not just a notebook with hidden state / out-of-order cells?

3. **Audit data reproducibility.** Can the exact training/eval dataset be regenerated — versioned snapshot, hash, query + cutoff? Is the data static or does it drift under a live query?

4. **Audit environment reproducibility.** Are dependencies pinned (lockfile/image digest)? Are Python, CUDA, and key library versions captured? Would a fresh machine rebuild the same env?

5. **Audit seeds and determinism.** Are seeds set for every RNG source (framework, numpy, dataloader, hashing)? Are nondeterministic ops (GPU kernels, parallel reductions, async data loading) identified and either pinned to deterministic mode or acknowledged in the tolerance?

6. **Audit config reproducibility.** Is the full resolved config captured per run (not just defaults), including paths and feature flags? Could a silent default change alter the result?

7. **Run the reproduce attempt (or design it).** Specify the exact steps to regenerate the target; where a step cannot be completed, that is a confirmed gap.

8. **Rank and remediate.** Order gaps by (blocking-ness × effort), and for each give a concrete fix that names the file/step it applies to.

**Output Format:**

A markdown audit report:
- **Reproduction Target & Tolerance** — what must reproduce, success criterion.
- **Axis Scorecard** — table: Axis | Status (OK / Degrading / Blocking / Unknown) | Evidence.
- **Confirmed Gaps (ranked)** — gap | consequence | remediation | effort.
- **Unknowns to Check** — what to verify and how.
- **Reproduce Procedure** — the corrected, step-by-step replay.
- **INSUFFICIENT EVIDENCE** — distinct from `Unknown` on a single axis: the audit-level verdict when no replay was attempted at all. Reproducibility is a property demonstrated by re-running, not inferred from the presence of a lockfile and a seed. Name the unblocking datum: one replay from a clean environment against the stated tolerance.

## Verification

- [ ] All five axes are assessed, each with a status and evidence.
- [ ] The reproduction tolerance is stated explicitly (bit-exact vs metric-within-ε).
- [ ] Every confirmed gap cites specific project evidence, not a generic item.
- [ ] Blocking gaps (cannot reproduce at all) are separated from degrading gaps (reproduces with variance).
- [ ] The reproduce procedure is concrete enough to follow without the original author.
- [ ] Where no replay was attempted, the overall verdict is INSUFFICIENT EVIDENCE — the presence of pinning artifacts is not itself evidence that a run reproduces.

## False-Positive Prevention

❌ **DON'T:**
- Declare a project reproducible because the script runs — running ≠ regenerating the reported number.
- Flag GPU nondeterminism as a blocking gap when the agreed tolerance is metric-within-ε.
- Assume data is versioned because it sits in a tidy folder; a live query underneath it still drifts.
- Treat "seeds are set" as sufficient without checking every RNG source and nondeterministic op.

✅ **DO:**
- Define tolerance first, then judge each gap against it — variance below tolerance is not a defect.
- Verify the data can be *regenerated to the same snapshot*, not merely that a file exists.
- Enumerate every randomness source and confirm each is seeded or accounted for in tolerance.
- Distinguish "confirmed gap" (reproduce step failed) from "unknown — needs check," and label accordingly.

## Example Output

```markdown
## Reproducibility Audit — Demand Forecast Model v4

### Reproduction Target & Tolerance
- Target: regenerate the reported test MAPE = 8.3%.
- Tolerance: MAPE within ±0.2 (GPU bit-exactness waived).

### Axis Scorecard
| Axis | Status | Evidence |
|---|---|---|
| Code | Degrading | Result came from a notebook; cells run out of order, no committed script. |
| Data | Blocking | Training set built from `SELECT ... WHERE date < now()` — drifts daily; no snapshot. |
| Environment | Degrading | `requirements.txt` unpinned (`pandas`, `torch` no versions); CUDA version unrecorded. |
| Seeds | Blocking | `torch.manual_seed` set, but dataloader `shuffle=True` unseeded; numpy unseeded. |
| Config | OK | Hyperparameters in a logged YAML; paths parameterized. |

### Confirmed Gaps (ranked)
1. **Data not snapshotted (Blocking, med effort).** The `now()` cutoff makes the dataset irreproducible. Fix: freeze to `date < '2026-05-01'`, snapshot to versioned table, log the hash.
2. **Unseeded RNG sources (Blocking, low effort).** Fix: set numpy + dataloader generator seeds; set `worker_init_fn`.
3. **Notebook-sourced result (Degrading, med effort).** Fix: export to a committed `train.py`; rerun from clean state.
4. **Unpinned env (Degrading, low effort).** Fix: generate a lockfile + record CUDA; rebuild and re-verify.

### Unknowns to Check
- Whether `torch.use_deterministic_algorithms(True)` is feasible given the conv layers — test for unsupported-op errors.

### Reproduce Procedure
1. Snapshot data at the frozen cutoff; record hash. 2. Rebuild env from lockfile. 3. Seed all RNGs. 4. Run `train.py`; expect MAPE 8.3% ± 0.2.
```

**Techniques Used:**
- **ST-02 (Structured Sequential Instructions):** target/tolerance → five-axis sweep → replay.
- **RT-05 (Evidence-Based Reasoning):** every gap is anchored to specific project evidence.
- **QA-04 (Consistency Checking):** the reproduce attempt is the consistency test of the audit.
- **DS-06 (Prioritization & Severity Guidance):** gaps ranked by blocking-ness × effort.
- **CM-02 (Constraint Specification):** the reproduction tolerance is the governing constraint.
