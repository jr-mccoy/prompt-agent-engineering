# Frontend TypeScript Type-Safety Audit

**Objective:** Audit a frontend TypeScript codebase for erosion of type safety — `any` leakage, unsafe assertions and non-null operators, missing or disabled strict compiler flags, unsound patterns, and untyped external boundaries — and deliver prioritized, evidence-based remediation that raises soundness without breaking the build.

**When to Use:**
- Use when: A codebase "uses TypeScript" but bugs that the type system should catch keep reaching runtime
- Use when: Planning to enable `strict` (or sub-flags) and needing to scope the work and risk
- Use when: Reviewing a codebase inherited or generated by tools, suspected of `any` proliferation and silent assertions
- Don't use when: You need to design the type API of a single component (use the component-typing prompt) or write runtime validation from scratch

## Instructions

1. **Establish the compiler-config baseline**
   - Read `tsconfig.json` (and extended/base configs); record `strict` and each sub-flag (`noImplicitAny`, `strictNullChecks`, `strictFunctionTypes`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, etc.)
   - Note disabled safety flags and any `// @ts-nocheck`/`// @ts-ignore`/`// @ts-expect-error` usage
   - Identify lint rules that govern types (e.g., `no-explicit-any`, `no-unsafe-*`) and whether they run in CI
   - Treat specific flag defaults/behaviors as "verify against current TypeScript docs" where versions matter

2. **Find `any` leakage and its blast radius**
   - Locate explicit `any` annotations and implicit `any` (where `noImplicitAny` is off)
   - Trace `any` propagation: a single `any` at a boundary often infects downstream code silently
   - Distinguish necessary/temporary `any` (with a comment and ticket) from accidental leakage
   - Flag `any[]`, `Record<string, any>`, and `Function`/`object` as broad escape hatches

3. **Audit unsafe assertions and escape hatches**
   - Find type assertions (`as Foo`, `as unknown as Foo`, angle-bracket casts) and assess whether each is justified or papering over a real mismatch
   - Flag non-null assertions (`!`) where the value can genuinely be null/undefined
   - Review `@ts-ignore`/`@ts-expect-error` for whether they hide fixable errors
   - Check definite-assignment assertions (`prop!: T`) and unchecked index access patterns

4. **Detect unsound patterns**
   - Look for unsafe narrowing and missing exhaustiveness checks (switches over unions without a `never` default)
   - Check function-type variance issues and event-handler/callback mismatches hidden by `any`
   - Identify mutation of readonly intent, and arrays/records accessed without bounds/key checks
   - Review enum vs literal-union misuse and casting between unrelated shapes

5. **Audit external/untyped boundaries**
   - API responses: are network payloads typed by assertion only, or validated (schema/parser) at the boundary?
   - Third-party libraries: any `@ts-ignore`d imports, missing `@types`, or hand-rolled `declare module 'x': any`
   - Browser/storage/env boundaries (`localStorage`, `JSON.parse`, `process.env`, `window`) returning `any`/`string | null` used unsafely
   - `unknown` usage: is it narrowed properly, or cast straight to a concrete type?

6. **Estimate effort to raise the baseline**
   - For each disabled strict flag, estimate the error volume and risk of enabling it (describe method; do not assert a count without compiling)
   - Identify which flags can be turned on incrementally (per-directory configs, staged adoption)
   - Recommend boundary validation where types currently rely on trust

7. **CRITICAL: Verify findings before reporting**
   - Confirm an `any`/assertion actually permits a real bug (not a benign, clearly-justified case) before flagging it as high severity
   - Trace whether a `!` non-null assertion is guaranteed safe by surrounding control flow before recommending removal
   - Validate that enabling a flag is feasible — note when it would require large, risky changes
   - **Confidence level** for each finding:
     - **High Confidence:** `any` or assertion demonstrably allows a real type mismatch, or a disabled flag clearly hides bugs
     - **Medium Confidence:** Pattern is unsound in general but may be guarded by surrounding logic
     - **Low Confidence:** Suspected issue whose impact needs compilation/flag-flip to quantify

8. **Prioritize remediation**
   - Rank by the severity of runtime bugs each fix prevents and by blast radius
   - Separate quick wins (lint rule, replacing obvious `any`, boundary parser) from staged work (enabling `strict` incrementally)
   - Recommend a safe enablement order for strict sub-flags

## False-Positive Prevention (MUST follow)

❌ **DON'T:**
- Treat every `any` as a defect — some are justified, temporary, and documented; judge by blast radius and intent
- Recommend deleting a non-null assertion that is actually guaranteed by preceding control flow
- Assert how many errors enabling a flag will produce without compiling — describe how to measure instead
- Flag `as const` or legitimate narrowing assertions as unsafe
- Demand runtime validation at every boundary regardless of trust level and cost
- Call `unknown` a problem — it is the safe escape hatch when narrowed properly
- Assert version-specific flag behavior from memory — verify against current TypeScript docs

✅ **DO:**
- Prioritize `any` at boundaries (where it propagates) over isolated, contained cases
- Verify control flow before recommending removal of `!` or an assertion
- Describe a measurement method (flip the flag in a branch, count errors) rather than guessing counts
- Recommend boundary validation (schema/parser) specifically where untrusted data enters typed code
- Propose incremental strict-flag adoption with a safe ordering and per-directory scoping
- Distinguish justified, documented escape hatches from accidental ones
- Note where behavior should be verified against current TypeScript/library docs

## Expected Output

A type-safety audit including:
- A compiler-config and lint baseline
- An `any`-leakage, unsafe-assertion, unsound-pattern, and boundary analysis
- Detailed findings with severity, confidence, location, and evidence
- A staged plan to enable strict flags safely
- Prioritized remediation split into quick wins and staged work

## Example Output

```markdown
## TypeScript Type-Safety Audit

### Executive Summary
The project compiles with `strict` off and `strictNullChecks` disabled, so null-related bugs are invisible to the compiler, and API responses are typed purely by assertion (`as User`) without validation — the single largest soundness gap. Explicit `any` clusters at the API and storage boundaries and propagates into UI state. Enabling `strictNullChecks` and validating API payloads at the boundary would prevent the majority of the runtime type errors seen in production logs.

### Compiler & Lint Baseline
| Flag / Rule | State | Risk if left as-is |
|-------------|-------|--------------------|
| strict | off | Multiple safety checks disabled |
| noImplicitAny | off | Implicit `any` spreads silently |
| strictNullChecks | off | Null/undefined bugs uncaught |
| noUncheckedIndexedAccess | off | `arr[i]` typed as defined when it may be undefined |
| @typescript-eslint/no-explicit-any | off | No guardrail against new `any` |

### Erosion Inventory
| Category | Observed | Notable locations |
|----------|----------|-------------------|
| Explicit `any` | Clustered at boundaries (count via lint scan) | `api/client.ts`, `lib/storage.ts` |
| Type assertions (`as`) | API responses cast to domain types | `api/*.ts` |
| Non-null assertions (`!`) | Mixed; some control-flow-guarded | `components/*` |
| `@ts-ignore` | Hides 2 library import errors | `lib/charts.ts` |
| Untyped boundaries | `JSON.parse`, `localStorage`, fetch payloads | `lib/storage.ts`, `api/client.ts` |

### Detailed Findings

#### Finding 1: API Responses Typed by Assertion, Not Validated
- **Severity:** High
- **Confidence:** High
- **Location:** `src/api/client.ts`
- **Evidence:**
  ```ts
  async function getUser(id: string): Promise<User> {
    const res = await fetch(`/api/users/${id}`);
    return (await res.json()) as User; // no validation; shape trusted blindly
  }
  ```
- **Impact:** A backend change or error payload yields a `User` that doesn't match its type; downstream code crashes at runtime with no compile-time signal.
- **Recommendation:** Validate at the boundary with a schema/parser and derive the type from the schema, so the type and runtime check stay in sync. Keep `as` only after successful validation.
- **Effort:** Medium

#### Finding 2: `strictNullChecks` Disabled
- **Severity:** High
- **Confidence:** High
- **Location:** `tsconfig.json`
- **Evidence:**
  ```jsonc
  { "compilerOptions": { "strict": false, "strictNullChecks": false } }
  ```
- **Impact:** `null`/`undefined` are assignable everywhere; "cannot read property of undefined" bugs are invisible to the compiler.
- **Recommendation:** Enable `strictNullChecks` incrementally. Method: flip it in a branch, compile, and count/triage errors by directory; fix leaf modules first, then shared ones. Do not assert the error count up front — measure it.
- **Effort:** High (staged)

#### Finding 3: `any` Leakage from Storage Boundary
- **Severity:** Medium
- **Confidence:** High
- **Location:** `src/lib/storage.ts`
- **Evidence:**
  ```ts
  export function read(key: string): any {
    return JSON.parse(localStorage.getItem(key) ?? 'null'); // any spreads to all callers
  }
  ```
- **Impact:** Every consumer of `read()` receives `any`, defeating type checking wherever stored data is used.
- **Recommendation:** Return `unknown` and require callers to narrow/validate, or accept a parser per call site:
  ```ts
  export function read<T>(key: string, parse: (v: unknown) => T): T | null { /* ... */ }
  ```
- **Effort:** Medium

#### Finding 4: Non-Null Assertion Without a Guarantee
- **Severity:** Medium
- **Confidence:** Medium
- **Location:** `src/components/Profile.tsx`
- **Evidence:**
  ```tsx
  const name = user!.name; // user can be undefined before load resolves
  ```
- **Impact:** Runtime crash during the loading window; the `!` silences the only warning.
- **Recommendation:** Guard with a loading/empty branch or optional chaining + fallback. Confirm there is no preceding control-flow guarantee before removing the `!`.
- **Effort:** Low

#### Finding 5: Non-Exhaustive Union Switch
- **Severity:** Low
- **Confidence:** Medium
- **Location:** `src/lib/reducer.ts`
- **Evidence:**
  ```ts
  switch (action.type) {
    case 'add': /* ... */ break;
    case 'remove': /* ... */ break;
    // no default; a new action type compiles silently and does nothing
  }
  ```
- **Impact:** Adding a new action type fails silently instead of surfacing at compile time.
- **Recommendation:** Add a `default` branch with a `never` exhaustiveness check so new variants become compile errors.
- **Effort:** Low

### Strict-Flag Enablement Plan
| Step | Flag | Scope | Approach |
|------|------|-------|----------|
| 1 | `noImplicitAny` | Repo | Annotate boundaries; low churn |
| 2 | `strictNullChecks` | Per-directory → repo | Fix leaf modules first; measure error count in a branch |
| 3 | `noUncheckedIndexedAccess` | Repo | Add guards on array/record access |
| 4 | `strict: true` (remaining) | Repo | Turn on once sub-flags are green |

### Prioritized Recommendations

#### Quick Wins (< 1 day each)
| # | Action | Impact | Effort |
|---|--------|--------|--------|
| 1 | Enable `@typescript-eslint/no-explicit-any` (warn) in CI | High - stops new leakage | 1 hour |
| 2 | Return `unknown` from `storage.read` and narrow at call sites | Medium - contains `any` | 4 hours |
| 3 | Add `never` exhaustiveness checks to union switches | Low - future-proofs reducers | 2 hours |

#### Staged Work (multi-day)
| # | Action | Impact | Effort | Dependencies |
|---|--------|--------|--------|--------------|
| 1 | Validate API payloads at the boundary with a schema | High - eliminates blind casts | 1 week | Schema lib chosen |
| 2 | Enable `strictNullChecks` directory by directory | High - catches null bugs | 1-2 weeks | Boundary validation first |

### Patterns to Preserve
- **Domain types co-located with API modules** — a good place to anchor boundary validation
- **`unknown` (where already used) narrowed before use** — the correct escape hatch
- **Documented, ticketed temporary `any`** — acceptable when intentional and tracked
```

## Techniques Used

- **ST-01 (Clear Objective Statement):** Scopes the audit to soundness erosion and safe remediation, not generic code review
- **ST-02 (Structured Sequential Instructions):** Steps move from config baseline to `any` to assertions to unsound patterns to boundaries to enablement
- **RT-02 (Multi-Dimensional Analysis Framework):** Separates config, `any` leakage, assertions, unsoundness, and boundaries as distinct axes
- **RT-05 (Evidence-Based Reasoning):** Findings cite code and explicitly defer error counts to measurement rather than guessing
- **DS-06 (Prioritization Guidance):** Provides a strict-flag enablement order plus quick-win vs staged remediation with dependencies
